# ADR-0001: Canonical stack selection

- Status: Accepted
- Date: 2026-09-11
- Extends: project-init ADR-0001, ADR-0004, ADR-0005
- Superseded by: None

## Context

my-web-2026 replaces my-web-2025 as the personal Web / Personal Web Platform
for 2026 and beyond. The initial release (`0.1.0` Foundation) is targeted for
2026-09 and the live-site cutover for 2026-10.

The user-facing goals are clear:

- A correct technical foundation
- Documented architecture boundaries
- Deterministic dev / build / test / deploy paths
- A weekly release sprint workflow that scales to AI agents and human
  contributors
- A `0.1.0` Foundation release that boots on Cloudflare even with no product
  features

We do **not** want to carry over toolchain decisions from my-web-2025
without verifying them against current official guidance.

## Decision

### 1. Runtime platform: Cloudflare Workers

Cloudflare is the deployment and runtime platform for every environment:

- Production, staging, and preview environments all run on Cloudflare Workers.
- The TypeScript reference for Workers, Wrangler, and the Vite plugin is the
  authoritative source for environment setup, not memory of older guides.

### 2. Web framework: TanStack Start

TanStack Start is the chosen web framework. It is supported by Cloudflare
Workers via the official Cloudflare TanStack Start guide and the
`@tanstack/react-start/plugin/vite` plugin.

Starter guidance was sourced from Cloudflare's current framework guide at
`/workers/framework-guides/web-apps/tanstack-start/` on 2026-09-11.

### 3. External HTTP boundary: Hono

Hono handles HTTP traffic that is **not** generated by the TanStack Start UI:

- External REST API endpoints (`/api/v1/*`)
- Inbound webhooks (`/webhooks/*`)
- OAuth callbacks (`/oauth/*`)
- Third-party integration adapters (`/integrations/*`)

Hono is mounted as a TanStack Start request middleware (`createMiddleware().server`)
inside `src/start.ts` so the canonical `wrangler.jsonc` `main: "@tanstack/react-start/server-entry"`
remains untouched. The middleware short-circuits external-boundary prefixes and
hands the rest of the request back to TanStack Start.

Internal application operations invoked from the UI are implemented as TanStack
Start server functions (`createServerFn`) and **must not** be exposed through
Hono.

### 4. Architecture style: Modular Monolith

The architecture is **deployment monolith / modular codebase / domain-oriented**:

- One repository.
- One primary Cloudflare Worker deployment.
- One wrangler config. Multiple Workers, microservices, or split databases are
  not introduced unless a concrete requirement emerges.
- Logical boundaries (frontend features, backend domains, Hono external
  boundary, Cloudflare infra adapters) are documented but kept in the same
  repository.

### 5. Frontend layout: feature-oriented

The frontend avoids a flat `components/`, `hooks/`, `utils/` mega-folder and
is organised around user-facing features (`portfolio`, `content`, `tools`,
`projects`, `activity`, `integrations`). Each feature owns its routes,
components, hooks, and styling.

Cross-feature imports go through an explicit public entry of the importing
feature. No implicit shared mutable state.

### 6. Backend layout: domain / application / adapters

The backend avoids premature Clean Architecture ceremony. The minimum useful
separation is:

```
domains/<name>/
  application/   - use cases, orchestration (no HTTP / no Cloudflare SDK)
  adapters/      - persistence, queue, cache, external-service adapters
  contracts/     - public types, events, schemas
```

Hono handlers and TanStack Start server functions both consume the same
application layer.

### 7. Styling: Panda CSS

Tailwind CSS is explicitly **not** adopted. Panda CSS is the styling system.

A design system foundation (raw tokens, semantic mapping, typography,
spacing, sizing, radii, shadows, breakpoints, motion, layout/grid
principles) is established at 0.1.0. Component recipes are introduced only
when an actual page implementation needs them. The system is owned by
my-web-2026; it is **not** imposed on external Tool submodules.

### 8. Tools: separate repositories, Git submodules

Existing Web Tools remain independent repositories. They are integrated into
my-web-2026 as Git submodules under `tools/<tool-name>/`.

Boundary rules:

- Parent never imports from inside a submodule `src`.
- Submodule never imports from my-web-2026 source via relative path.
- Each Tool may use its own framework, style system, and runtime.
- my-web-2026's Panda CSS / Design System is **not** forced on Tools.
- Tool commit SHAs are pinned as the verified version on the parent side.

`0.1.0` does not add any concrete Tool submodule yet. The architecture
leaves room for a future Tool Registry / manifest / build orchestration.

### 9. Persistence: D1 for structured content, R2 for blobs

CMS structured content lives in Cloudflare D1 as the source of truth. R2 is
used for image / video / download blobs.

The previous my-web-2025 model of syncing a SQLite database file to R2 is
**not** inherited.

CMS revision model requirements (draft / published revision / revision
history / preview / publish / rollback) are documented but **not** built at
0.1.0. The database schema is intentionally minimal at 0.1.0 — only
Foundation smoke checks are wired.

### 10. Cloudflare service selection

Cloudflare services are chosen by purpose, not by inventory:

| Service                | Decision at 0.1.0                                      |
| ---------------------- | ------------------------------------------------------ |
| Workers                | Adopt (core runtime)                                   |
| D1                     | Adopt only when a feature requires it                  |
| R2                     | Adopt only when a feature requires it                  |
| Queues                 | Defer until webhook / async processing is needed       |
| KV                     | Defer until a need appears                             |
| Durable Objects        | Defer until realtime / stateful coordination is needed |
| Workflows              | Defer until durable multi-step processing is needed    |
| Vectorize / Workers AI | Defer until a clear product requirement exists         |

The 0.1.0 Worker bundle includes only the static assets binding
(`assets: { directory: "./dist/client", binding: "ASSETS" }`).
No D1, R2, KV, Queues, Durable Objects, or Workflows are provisioned in
the initial `wrangler.jsonc`.

## Consequences

### Positive

- All initial decisions trace back to a current official source.
- The Cloudflare + TanStack Start + Hono + Panda CSS combination is
  verified end-to-end (vite build + wrangler dry-run both succeed).
- The internal/external split between TanStack Start server functions
  and the Hono boundary is enforced at the middleware layer, not by
  convention.
- The architecture stays a modular monolith until proven otherwise.

### Negative / Trade-offs

- The Tailwind ecosystem (shadcn, etc.) is not directly available.
- Submodule-based Tools require extra CI plumbing before they can land.
- D1 / R2 / Queues / etc. are not wired yet, so 0.1.0 has minimal
  persistence surface area.

## Re-evaluation triggers

Re-evaluate this ADR when:

- TanStack Start, Hono, Panda CSS, or Cloudflare Workers guidance changes
  in a way that invalidates any of the above choices.
- A product feature in 0.2.0 or later genuinely requires multiple Workers,
  a microservice split, KV, Durable Objects, Workflows, Vectorize, or Workers AI.
- The Tools / Design System boundary becomes a bottleneck for shipping.
