# ADR-0001: Canonical stack selection

- Status: Accepted (revised 2026-09-19)
- Date: 2026-09-11
- Extends: project-init ADR-0001, ADR-0004, ADR-0005
- Superseded by: None

## Context

my-web-2026 replaces my-web-2025 as the personal Web Platform for
2026 and beyond. The initial release (`0.1.0` Foundation) is targeted
for 2026-09 and the live-site cutover for 2026-10.

A first-pass initialization (2026-09-11) reached "build / dry-run
green" but the foundation review identified multiple P0 wiring issues
that this revision corrects. Stack selection itself is preserved;
only the implementation shape changes.

## Decision

### 1. Runtime platform: Cloudflare Workers

Cloudflare is the deployment and runtime platform for every environment:
production, staging, and preview. Wrangler + `@cloudflare/vite-plugin`
+ `@cloudflare/vitest-plugin` is the toolchain.

### 2. Web framework: TanStack Start

TanStack Start is the chosen web framework. The default server-entry
is used unchanged — `src/start.ts` is intentionally absent so the
default CSRF middleware is active. Adding a custom `startInstance`
override requires an ADR.

### 3. External HTTP boundary: Hono (at the Worker entry, not in TanStack Start middleware)

Hono handles HTTP traffic that is **not** generated by the TanStack
Start UI:

- External REST API endpoints (`/api/v1/*`)
- Inbound webhooks (`/webhooks/*`)
- OAuth callbacks (`/oauth/*`)
- Third-party integration adapters (`/integrations/*`)

Hono is mounted at the **Worker entry** (`src/server.ts`) — not as
TanStack Start middleware. The custom entry's `fetch(request, env,
ctx)` checks the path prefix and dispatches either to Hono
(`externalBoundary.fetch(request, env, ctx)`) or to the TanStack Start
default handler (`handler.fetch(request)`). This gives Hono real
`env` and `ctx` so future D1 / R2 / Queues adapters are not blocked
by a middleware stub.

Internal application operations invoked from the UI are implemented
as TanStack Start server functions (`createServerFn`) and **must not**
be exposed through Hono.

### 4. Architecture style: deployment monolith, obligation-oriented source

The architecture remains one repository, one primary Cloudflare Worker,
and one wrangler config.

Source does not use a fixed layer or feature template. Durable boundaries
follow ADR-0008: governing invariant, decision authority, dependency direction,
and lifecycle determine ownership; path is the resulting projection.

### 5. Layout: observed obligations, not a template

0.2.0 currently exposes `home/`, `editorial/`, `cloudflare/`, and
`http/` alongside framework-owned `routes/` and runtime entrypoints.

This list is descriptive, not a schema for future features. A new capability
does not copy the Home tree by default. It establishes only the boundaries
justified by its own obligation and observed change pressure.

### 6. Styling: Panda CSS

Tailwind CSS is explicitly **not** adopted. Panda CSS is the styling
system.

Both **raw** and **semantic** token layers are owned by the shipped editorial
visual language (`src/editorial/tokens.ts` +
`src/editorial/semantic-tokens.ts`). Primitives are introduced only when an
actual surface needs them. A generic shared design-system layer is not
pre-created; a future visual language remains independent until a shared
obligation is observed. The host visual language is not imposed on external
Tool submodules.

### 7. Format and lint: Biome

Biome (`@biomejs/biome` 1.9.x) replaces both Prettier and ESLint.
A single binary handles format + lint, with two scripts:

- `pnpm run format` (`biome format --write`) — developer convenience.
- `pnpm run format:check` (`biome format`) — read-only gate.
- `pnpm run lint:check` (`biome lint`) — read-only gate.

The `validate:*` gates only ever invoke the read-only variants.

### 8. Design-system preview: Storybook

Storybook 8.6.x is the canonical preview surface for currently owned visual
language primitives (`src/editorial/primitives/<Name>.tsx` + adjacent
`<Name>.stories.tsx`). It is dev-time only; the static
build (`pnpm run build-storybook` → `storybook-static/`) is part of
`validate:integration` so a broken story fails the PR gate, but the
static output is gitignored.

### 9. End-to-end smoke: Playwright (chromium)

Playwright 1.63.x is the canonical E2E runner at 0.1.0. The 0.1.0
suite is HTTP-only (`request` fixture, no browser launch), covering
the four documented public surfaces (`/`, `/api/v1/health`,
`/api/v1/db/ping`, `/api/v1/media/ping`). The same spec runs against
`pnpm dev` locally and against the deployed Worker URL when
`PLAYWRIGHT_BASE_URL` is set. Browser-based specs land in 0.2.0.

### 10. Tools: separate repositories, Git submodules

Existing Web Tools remain independent repositories. They are
integrated into my-web-2026 as Git submodules under
`tools/<tool-name>/`. Boundary rules (parent <-> submodule) are
unchanged; see [ADR-0006](ADR-0006-tools-submodule-policy.md).

`0.1.0` does not add any concrete Tool submodule yet. The
architecture leaves room for a future Tool Registry / manifest /
build orchestration.

### 11. Persistence: D1 for structured content, R2 for blobs

CMS structured content lives in Cloudflare D1 as the source of truth.
R2 is used for image / video / download blobs. D1 (`DB`) and R2
(`MEDIA`) bindings are declared in `wrangler.jsonc` at 0.1.0 with
placeholder ids; both have a Vitest SELF smoke in
`test/integration/`.

### 12. Cloudflare service selection

Cloudflare services are chosen by purpose, not by inventory:

| Service                | Decision at 0.1.0                                      |
| ---------------------- | ------------------------------------------------------ |
| Workers                | Adopt (core runtime)                                   |
| Static Assets          | Adopt (`ASSETS`)                                       |
| D1                     | Adopt (`DB`, placeholder database_id)                  |
| R2                     | Adopt (`MEDIA`, placeholder bucket)                    |
| Queues                 | Defer until webhook / async processing is needed       |
| KV                     | Defer until a need appears                             |
| Durable Objects        | Defer until realtime / stateful coordination is needed |
| Workflows              | Defer until durable multi-step processing is needed    |
| Vectorize / Workers AI | Defer until a clear product requirement exists         |

## Consequences

### Positive

- All initial decisions trace back to a current official source.
- The Cloudflare + TanStack Start + Hono + Panda CSS combination is
  verified end-to-end (`validate:release` passes against the rebuilt
  Worker).
- The internal/external split between TanStack Start server functions
  and Hono is enforced at the Worker entry, with real `env` and
  `ctx` reaching Hono.
- Default CSRF middleware is active without explicit configuration.
- The deployment stays monolithic while source boundaries follow observed obligations.

### Negative / Trade-offs

- The Tailwind ecosystem is not directly available.
- Submodule-based Tools require extra CI plumbing before they can
  land.
- The semantic token layer is intentionally short; new tokens are
  introduced through design-system ADRs.

## Re-evaluation triggers

Re-evaluate this ADR when:

- TanStack Start, Hono, Panda CSS, or Cloudflare Workers guidance
  changes in a way that invalidates any of the above choices.
- A product feature in 0.2.0+ genuinely requires multiple Workers,
  KV, Durable Objects, Workflows, Vectorize, or Workers AI.
- The Tools / Design System boundary becomes a bottleneck.
- Coverage thresholds become meaningful and need re-introduction.
