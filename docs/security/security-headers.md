# Security headers — the shipped contract (Issue #449)

> What `X-Content-Type-Options`, `Referrer-Policy` and
> `Permissions-Policy` say on every response my-web-2026 serves, which
> module owns the decision, and how a Tool earns a browser
> capability. Read this before editing `public/_headers`,
> `src/http/security-headers.*`, or a Tool's `delivery.iframe` block.

## 1. Two surfaces, one set of values

Cloudflare documents that *custom headers defined in the `_headers` file
are not applied to responses generated by your Worker code, even if the
request URL matches a rule*. So the site carries these headers in two
places that no single function can produce:

| Surface | Serves | Owner |
| --- | --- | --- |
| `src/http/security-headers.ts` | Everything the Worker generates: SSR documents, redirects, `/_serverFn/*`, `/api/v1/*` JSON and errors | `src/http/**` |
| `public/_headers` | Everything Cloudflare Static Assets serves: `/assets/*`, `/share/**`, Tool artefacts, favicon | `src/http/**` values, Static Assets delivery |

The canonical **values** live in
[`src/http/security-headers.json`](../../src/http/security-headers.json).
Both surfaces are asserted against it by
`node scripts/check-security-headers.mjs`, which is wired into
`pnpm run validate:fast`. Editing one side without the other is a red
gate, not a silent inconsistency.

`src/server.ts` mounts the policy **after** the Hono / TanStack Start
dispatch, so the single choke point covers both branches:

```ts
const response = matchesExternalBoundary(url.pathname)
    ? await externalBoundary.fetch(request, env, ctx)
    : await handler.fetch(request);
const secured = applySecurityHeaders(request, response, toolRouteSecurityPolicy(url.pathname));
return applyHtmlCachePolicy(request, secured);
```

## 2. Values

| Header | Value | Why |
| --- | --- | --- |
| `X-Content-Type-Options` | `nosniff` | OWASP ASVS V14.1.1. The site serves user-influenced bytes (reaction payloads, admin image uploads, `/share/**` PDFs); without it a response fetched under the wrong `Content-Type` may be re-interpreted as HTML or script. |
| `Referrer-Policy` (host) | `strict-origin-when-cross-origin` | Keeps the origin, drops the path on cross-origin requests. The referrer never carries a page path to GA4 or to anything else off-origin. |
| `Referrer-Policy` (Tool artefact) | `no-referrer` | A Tool bundle is third-party-shaped content. It gets no reason to know the host URL at all. Matches `delivery.iframe.referrer_policy` in the manifest. |
| `Permissions-Policy` | deny list, below | Explicit, not deny-all. |

### The deny list, and why it is not deny-all

```
bluetooth=(), camera=(), display-capture=(), geolocation=(), hid=(),
microphone=(), payment=(), serial=(), usb=(), xr-spatial-tracking=()
```

Every listed feature has no plausible use on this site: hardware
bridges (`bluetooth`, `hid`, `serial`, `usb`), capture devices
(`camera`, `display-capture`, `geolocation`, `microphone`), and
platform-gated products (`payment`, `xr-spatial-tracking`).

A feature that is **not** listed keeps the browser default allowlist
(`self`). That is deliberate: it means a future Tool that needs a new
capability can be granted it per Tool without amending the host
baseline first, and it keeps the baseline honest — every entry has to
justify itself. `/admin` copies invitation URLs with
`navigator.clipboard`; that works precisely because `clipboard-write`
is not on the list.

## 3. How a Tool earns a capability

`microphone` is denied everywhere by default, and exactly one Tool
needs it (`mic-level`, Issue #81 follow-up). The requirement is
declared once, in the Tool manifest, and read by three consumers:

```jsonc
// src/tools/manifest.json — mic-level
"delivery": {
  "kind": "host_disabled",
  "iframe": { "sandbox": "allow-scripts", "referrer_policy": "no-referrer", "allow": "microphone" }
}
```

1. **Data** — `delivery.iframe.allow`. Feature NAMES only
   (`"microphone"`). The host owns the origin allowlist, because only
   the host knows which origin actually served the response.
2. **Registry** — `toolRouteSecurityPolicy(pathname)`
   (`src/tools/registry.ts`) resolves the declaration into
   `{ referrerPolicy, grantedPermissions }` per path. `src/server.ts`
   hands that to `applySecurityHeaders`.
3. **Container** — the shell route renders
   `<iframe allow="microphone">` (`src/routes/tools.$slug.tsx`).
4. **Document** — `public/_headers` grants the same feature on
   `/tools/mic-level/app/*`.

Steps 3 and 4 are the two halves of the browser contract, and
Permissions Policy needs both: the container opts the feature **in**,
and the framed document must not deny it in its own response header.
`scripts/check-security-headers.mjs` fails if a grant exists on one
half only, or if a feature is granted anywhere outside the declaring
Tool's namespace.

### Why the grant is origin-scoped

The emitted value is `microphone=(self "https://rebuildup.dev")` in
production and `microphone=(self "http://127.0.0.1:8787")` in local
workerd. The Worker half derives the origin from the request, so the
grant is always scoped to the origin that actually served it. The
`_headers` half is static text and therefore carries the canonical
production origin (ADR-0014); that is recorded as a known constraint
below.

### `_headers` rule order is load-bearing

Rules are ordered least-specific first. Every matching rule
contributes its headers and a later rule overrides an earlier one for
the same header, so the `/*` baseline sits at the top and each
narrowing rule below it wins. Appending a new wildcard rule at the
bottom would silently undo the Tool rules — the check models the same
order and fails if the effective value changes.

### Automated

| What | Command |
| --- | --- |
| Worker responses (real routes, real workerd) | `pnpm exec vitest run test/integration/security-headers.test.ts` |
| Policy logic (deny list, grant, origin scope, sealed headers) | `pnpm exec vitest run src/http/security-headers.test.ts` |
| Tool grant resolution | `pnpm exec vitest run src/tools/registry.test.ts` |
| Static Assets parity + grant namespace | `node scripts/check-security-headers.mjs` |

| Regenerate the verification screenshot | `node scripts/security-header-report.mjs` |

The integration suite prints its measurements as
`SECURITY_HEADERS_MEASUREMENT <json>`; the verification report under
[`docs/verification/security/`](../../docs/verification/security)
renders them rather than restating them.

### Measured locally

`pnpm preview` (the `@cloudflare/vite-plugin` preview server) serves the
real Worker plus the built Static Assets and parses `public/_headers`,
so both halves are observable on a laptop:

```bash
pnpm run build                     # vite build + Tool artefacts
pnpm preview -- --port 4123
curl -sSI http://127.0.0.1:4123/contact                     | grep -iE 'nosniff|referrer|permissions'
curl -sSI http://127.0.0.1:4123/share/procon2026/index.html | grep -iE 'nosniff|referrer|permissions'
```

Tool artefacts are only present when the Tool submodules are checked
out; with the submodules absent the path 404s and the `_headers` rule
for it is not exercised. The parity check covers that case instead,
by asserting the rule values rather than a live response.

## 5. Known constraints

- `_headers` is static, so the Tool-artefact grant names the canonical
  production origin rather than the request origin. This only matters
  for a locally-served Tool artefact, where the frame loses the
  microphone (fail-closed).
- `mic-level` is still `host_disabled`, so the grant is verified at the
  header / resolution level, not by an actual capture. The Tool-side
  standalone build is the remaining blocker (Issue #81 follow-up).
- `readmark` additionally needs `Cross-Origin-Opener-Policy` /
  `Cross-Origin-Embedder-Policy` for `SharedArrayBuffer` pdfjs decode.
  Those headers change the site's isolation model (they gate
  cross-origin popups such as OAuth), so they are deliberately NOT
  part of this contract and need their own ticket.
- `Content-Security-Policy` is out of scope for #449. Adding a CSP to
  a TanStack Start app with a Tool iframe is a separate decision with
  its own breakage surface.
